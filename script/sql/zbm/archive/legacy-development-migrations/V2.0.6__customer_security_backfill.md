# V2.0.6 Customer 历史身份回填运行手册

V2.0.6 的 DDL 只建立安全字段和最终唯一约束，不在 SQL 中处理明文、AES 密钥或 HMAC 密钥。历史数据必须由应用侧维护任务使用与线上完全相同的 `@EncryptField` AES 配置和 `CustomerIdentityFingerprintService` 回填。

执行顺序：

1. 进入维护窗口，停止所有 Customer 新增、修改和逻辑删除入口；后台任务和消息消费者也必须停止。数据库账号不得临时绕过这一写入冻结。
2. 执行迁移前查询，按应用的 NFKC、去空白、转大写规则计算 `(id_type, identity_fingerprint)`；发现有效记录重复时立即停止，由人工合并或修正，禁止自动删除。
3. 执行 `V2.0.6__customer_security_columns.sql`。DDL 失败时不要重复执行，先依据 `information_schema` 判断已经完成到哪一步。
4. 应用按主键升序、小批量事务锁定 Customer。对每条有证件的记录：解密已有 `ENC_` 密文或读取受控历史明文，计算独立 HMAC 指纹，使用 AES 写回 `ENC_` 密文，同时写入 `pii_key_version`。任何一条加密、解密、指纹或唯一约束失败都回滚该批次并停止后续批次。
5. 验证所有 `del_flag = '0'` 且证件非空的记录均满足：`id_no` 为 `ENC_` 密文、`identity_fingerprint` 长度为 32、`pii_key_version` 非空；再次检查有效身份无重复。
6. 用抽样只读验证确认应用能够解密，并确认日志、异常和审计记录没有明文或密钥后，才恢复 Customer 写入口。

失败恢复：DDL 属于 MySQL 隐式提交操作，不依赖事务整体回滚。应用回填采用可重入批次，以 `identity_fingerprint IS NULL` 或缺少密钥版本定位未完成记录；已成功回填的数据保持不动。AES 密钥丢失将导致密文不可恢复，HMAC 密钥丢失将导致无法稳定查重；两者都必须由外部密钥管理系统独立备份，且不得互相替代。
