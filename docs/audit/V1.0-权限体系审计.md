# V1.0 权限体系审计

## 1. 真实权限模型

当前权限不是单层菜单控制，而是四层叠加：

1. **身份与 SuperAdmin**：固定超级管理员用户/角色 ID，`LoginHelper.isSuperAdmin()` 触发统一旁路。
2. **功能权限**：角色—菜单—权限码，Controller 使用 `@SaCheckPermission`，Service 的 `PropertyFunctionalPermissionServiceImpl` 也会直接读取用户菜单权限。
3. **业务上下文**：`BusinessContext` + `ReferenceType` 控制前端 option/初始化接口可读取哪些引用数据。
4. **资源范围**：物业使用项目范围与业务域，仓储使用公司/项目/仓库关联范围；详情和写操作再做资源归属校验。

主要证据：

- `ruoyi-modules/ruoyi-system/src/main/java/org/dromara/system/service/impl/SysPermissionServiceImpl.java`
- `ruoyi-common/ruoyi-common-security/src/main/java/org/dromara/common/security/business/BusinessContext.java`
- `ruoyi-common/ruoyi-common-security/src/main/java/org/dromara/common/security/business/BusinessContextAccessService.java`
- `ruoyi-modules/ruoyi-property/src/main/java/org/dromara/property/scope/`
- `ruoyi-modules/ruoyi-warehouse/src/main/java/org/dromara/warehouse/security/WarehouseAccessService.java`

## 2. SuperAdmin 边界

- SuperAdmin 获得角色 `admin` 与通配权限，菜单与项目范围查询走全量。
- 非 SuperAdmin 不能维护项目管理授权，不能委派/修改含客户敏感权限的角色。
- `PropertyWorkspaceProjectServiceImpl`、`PropertyProjectScopeServiceImpl`、`WarehouseAccessService` 均有明确 SuperAdmin 旁路。
- 风险：旁路散布于 system/property/warehouse 多处。新增业务若忘记使用统一服务，可能形成规则分叉；当前测试覆盖了若干旁路，但缺少统一架构约束测试覆盖所有 Service。

## 3. 角色、菜单与接口权限

- 后端权限码以 `module:business:action` 为主，菜单 SQL维护角色菜单关系。
- `RoleDelegationGuardImpl` 对 admin、超级管理员角色及客户敏感权限进行保护。
- `PermissionContractAuditTest`、`PropertyBusinessRolePermissionTest` 本轮均通过。
- migration V2.0.32～V2.0.36 对物业业务角色、权限归属和菜单类型持续收敛；但因无可验证 migration history，数据库当前实际角色菜单状态不能由仓库证明。

## 4. 项目与 BusinessContext

- `PropertyBusinessDomain` 区分项目、资源、客户关系、财务、仓库等域；`ProjectBusinessAction` 区分 READ/WRITE/EXPORT/OPTION。
- 项目范围由项目成员和管理授权贡献，列表查询使用范围，详情/写操作使用 `assertBusinessAccess`。
- `BusinessContext` 明确覆盖客户关系、住户、应收、收款、收费绑定及仓储查询/维护上下文。
- option Controller 即使没有直接权限注解，也通过 `BusinessContextAccessService` 与项目/仓库 Service 再授权；这是设计的一部分，不能误删。

## 5. 登录后项目初始化

前端 `src/permission.ts` 在首次获取用户信息并生成动态路由后调用 `useCurrentProjectStore().initialize()`。初始化规则：

- `currentProjectPolicy.ts` 仅当用户具有物业工作区权限或 `*:*:*` 时请求 `/property/workspace/projects`。
- 后端候选项目来自真实项目业务范围；前端注释明确当前项目只是 UI 偏好，不是授权来源。
- 缓存键包含 userId；保存项目不在新候选集时会清除并提示；仅一个候选时自动选择。
- 仓储明确不复用全局物业项目，使用仓库上下文。

可复现风险：

| ID | 等级 | 条件 | 风险/证据 |
|---|---|---|---|
| A-01 | P1 | 数据库未按 V2.0.32～V2.0.36 完整、按序执行 | 角色菜单与代码权限码可能漂移；仓库无自动 history 可证明执行状态 |
| A-02 | P2 | 新增物业权限码但未同步 `PROPERTY_WORKSPACE_PERMISSIONS` | 用户可能进入页面却不初始化工作项目；证据：前端 `currentProjectPolicy.ts` 是手工白名单 |
| A-03 | P2 | 新增上下文接口但未登记 `BusinessContext`/映射策略 | Controller 看似可访问，Service 会拒绝或误放引用数据；证据：枚举与访问服务为显式映射 |
| A-04 | P2 | 直接调用 Mapper 绕过项目/仓库 access service | 详情/导出可能越权；当前核心 Service 多数已显式校验，但没有全仓静态规则阻止未来绕过 |
| A-05 | P2 | 前端按钮仅靠 `v-hasPermi` 隐藏 | 不能替代后端校验；需保持 Controller/Service 双层控制 |
| A-06 | P3 | 登录态内权限被后台变更但前端未重新拉取 user info | 当前 session 仍可能展示旧按钮/项目候选；后端仍应最终拒绝 |

## 6. 列表、详情、导出与操作

- 物业核心列表通常先计算项目范围；详情取得实体后校验其 projectId；写操作在事务前后做项目访问校验。
- 应收/收款导出使用独立 EXPORT action，不应与 list 权限合并。
- 仓库详情与单据操作通过 `WarehouseAccessService.requireWarehouse` 或 `requireEnabledWarehouse`；物料另做公司范围校验。
- 客户 PII 查看/导出使用独立敏感权限和审计表，不等同于普通客户 list 权限。

## 7. 结论

权限架构方向完整，且有较多单元/契约测试；主要风险不是“完全没有权限控制”，而是手工 migration 状态不可证明、前端工作区权限白名单需人工同步、以及新增代码绕过统一范围服务时缺少全仓自动门禁。
