# TASK-V1-005 阶段 A：工程模块与数据库基线只读审计

审计日期：2026-10-14  
审计范围：后端 `zbm-platform`、前端 `zbm-platform-ui`、WSL `archlinux` 中的 `jdpm-mysql` / `jdpm-redis`。  
执行边界：本阶段仅做静态分析和数据库只读查询；未删除文件、未修改 POM/Java/Vue/SQL、未执行 migration、未写数据库、未清理测试数据，也未进入阶段 B/C/D。

## 1. 阶段 A 结论

1. 实际仓库不存在名为 `ruoyi-module` 的模块；存在的是 `ruoyi-modules`。它是 9 个模块的 Maven 聚合入口，属于构建结构，不能按“名称像示例”删除。
2. 可优先提出清理确认的模块是 `ruoyi-demo` 和 `ruoyi-job`：前者是明确的演示能力，后者现有 9 个执行器均为框架示例/账单示例，未发现物业业务模块调用。但二者当前都被 `ruoyi-admin` 直接依赖，不能只删除目录。
3. `ruoyi-ai` 当前开发/生产配置关闭，业务核心无调用，但仍存在后端模块、公共 AI 模块、前端页面、菜单、独立服务、Docker/Nginx 配置，属于“产品未启用但有完整间接引用”，须整链确认后清理。
4. `ruoyi-workflow` 不能认定无用：配置默认 `warm-flow.enabled=true`，后端 108 个 Java 文件、前端 12 个页面、14 个 API/类型文件，并在 `ruoyi-api` 暴露契约；但当前 `zbm-data` 没有任何 `flow_*` 表，部署完整性本身存在风险。
5. `ruoyi-gen` 是运维/开发工具而非物业业务，当前有菜单、页面、Controller 和 `gen_*` 表；是否从生产包剥离应由产品部署策略决定，阶段 A 不建议直接删除。
6. 当前开发配置明确连接 `zbm-data`（MySQL）和 Redis DB 0；实测 `zbm-data` 有 61 张表、无 `flyway_schema_history`。仓库也未发现 Flyway Maven 依赖或运行配置，因此当前 37 个 `V2.0.1`～`V2.0.36` SQL 是手工 migration 链，不是可由 Flyway 验证的历史。
7. 开发库包含项目、客户、应收、收款、仓储入库等业务测试数据；MySQL 使用 Docker volume 持久化，但未在常见备份目录发现 SQL/dump 文件。数据卷不等于可验证备份，因此禁止直接重建现库。
8. 当前 baseline 不是“全系统单一基线”：`script/sql/ry_vue.sql` 定义 24 张核心/示例表，`script/sql/zbm/baseline/01_schema.sql` 定义 37 张 HR/物业/收费/仓储表；工作流和 SnailJob 又各有独立 SQL。新 V1 的最终范围必须先随模块去留冻结。

### 3.1 现行 migration 状态

- 仓库有 37 个版本文件，版本范围 `V2.0.1`～`V2.0.36`，包括 `V2.0.33.1`。
- `script/audit/Get-ZbmMigrationManifest.ps1` 能校验数量、边界和 SHA-256；现有清单见 [V1.0-Migration版本清单](V1.0-Migration版本清单.md)。
- 数据库没有 Flyway history，无法从数据库自动证明每个版本是否执行。
- 历史文档记录部分脚本曾手工执行，但这不构成完整、机器可校验的版本账本。
- baseline 文件头仍写 `V2.0.33`，而 migration 已到 `V2.0.36`；`99_init.sql` 只 SOURCE 到 V2.0.32/33，和 `00_readme.sql` 列出的 V2.0.33.1 也不一致。这是重整前必须消除的基线元数据漂移。

## 4. V1 基线重整方案（提案，未实施）

### 4.1 决策顺序

1. 先确认 demo/job/AI/workflow/gen 的 V1 去留。
2. 冻结需保留的运行模块和数据库对象。
3. 从**已确认结构来源**生成一个完整、可审阅的 V1 权威 SQL；不能直接从含测试数据的开发库整库导出。
4. 初始化数据拆成：系统必需数据、V1 菜单/权限/字典、开发测试 seed 三类。
5. 接入 Flyway 后，在新的空库（建议新建 `zbm_v1_baseline_verify`，名称可确认）只执行 `V1__initial_schema.sql`。
6. 验证 `migrate`、`validate`、第二次 `migrate` 无重复 DDL，再进行 Mapper/登录/权限/物业/收费/仓储回归。
7. 验证完成且取得阶段 D 明确授权后，才讨论备份和切换原开发库。

### 4.2 建议目录与权威来源

优先沿用现有 `script/sql/zbm/`：

```text
script/sql/zbm/
├── baseline/
│   ├── zbm_initial_schema.sql      # 人工可读快照，由 V1 生成或与 V1 校验一致
│   └── README.md
├── migration/
│   ├── V1__initial_schema.sql      # Flyway 唯一执行权威
│   └── README.md
└── seed/
    └── dev/                        # 仅开发测试数据，不进入生产 migration
```

避免长期手改两份完整 SQL。建议以 `V1__initial_schema.sql` 为执行权威，baseline 快照由同一源生成并通过 SHA/结构检查保持一致。

### 4.3 初始化数据边界

纳入 V1：系统参数、必需内置角色、V1 菜单和权限、业务字典、必要客户端/OSS 配置（敏感值改为部署变量或明确占位）。  
排除 V1：开发账号、测试项目/员工/客户、房屋样例、应收/收款/冲销、库存余额/流水、出入库/调拨/盘点单、日志、消息和 `test_*` 示例数据。

## 6. 风险

| 等级 | 风险 | 控制措施 |
|---|---|---|
| P0 | 未验证备份即重建 `zbm-data` 会造成不可恢复的数据丢失 | 阶段 D 前制作并恢复验证备份；当前禁止任何 DROP/TRUNCATE |
| P1 | 无 Flyway history，不能证明历史脚本执行状态 | 不向现库伪造 V1；新空库从 V1 起步，旧库另行制定切换方案 |
| P1 | baseline、README、`99_init.sql` 的版本与包含范围不一致 | 阶段 C 一次性重整并自动校验 |
| P1 | 工作流默认开启但开发库无工作流表 | 先冻结产品范围，再选择完整纳入或完整移除 |
| P1 | 模块删除涉及 POM、自动扫描、前端、菜单、Docker 多端 | 按整链清单实施，每批独立构建和回归 |
| P2 | 物理外键为 0，纯 DDL 难以表达逻辑关联 | 基线文档显式记录逻辑关联，保留 Service 防护测试 |
| P2 | 开发配置包含固定数据库/Redis凭据 | 基线重整不复制凭据；部署配置另行环境化 |
