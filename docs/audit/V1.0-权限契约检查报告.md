## 工作项目策略

`PROPERTY_WORKSPACE_PERMISSIONS` 只列物业页面权限，不包含 `warehouse:*`。新增测试验证仅拥有 `warehouse:inventory:list` 时不会请求物业项目、不会自动加载物业项目。原策略保持：单项目自动选择、多项目允许切换；前端当前项目只用于界面上下文，后端仍通过项目/仓库访问服务授权。

## BusinessContext 显式映射

`BusinessContextPolicy` 为每个上下文声明权限组合（ANY/ALL）和允许的 `ReferenceType`。覆盖客户关系、住户、应收、收款、收费绑定，以及入库、出库、调拨、盘点、库存、库区、库位、物料等上下文。`BusinessContextPolicy.find` 对未登记/空上下文返回 empty，调用方默认拒绝。

自动化结果：

- `BusinessContextAccessServiceTest`：覆盖映射完整性、引用类型边界、AND/ANY 以及未知上下文 fail-closed；通过。
- `WorkspaceProjectPermissionPolicyTest`：覆盖物业权限触发、仓储权限不触发、SuperAdmin；通过。
- `PermissionContractAuditTest`：生成 `ruoyi-admin/target/permission-contract.csv` 并校验菜单/角色/接口契约；6/6 通过。

## 项目与仓储范围抽查

- 物业资源、客户、住户、收费项目/规则/绑定、应收、收款相关 Service 注入并调用 `PropertyProjectScopeService`，对应安全单测覆盖列表、详情或写操作。
- 仓库、库区、库位、物料、库存流水、入库、出库、调拨、盘点 Service 注入 `WarehouseAccessService`，对应 Service 单测覆盖访问拒绝路径。
- `BusinessContextAccessService` 未依赖前端当前项目，也未直接替代上述范围服务；测试明确约束该分层。

## 风险

- 静态脚本不能理解所有动态 Service 权限，因此仅将“菜单缺失”作为硬失败，合法差异由 Java 契约测试确认。
- 业务角色实际数据仍依赖 migration 正确执行；当前没有可信 Ledger，无法仅凭仓库 SQL证明每个环境均已应用。
- 新增物业页面必须同步 `PROPERTY_WORKSPACE_PERMISSIONS` 与测试；新增上下文必须同步 `BusinessContextPolicy`，否则 fail-closed。
