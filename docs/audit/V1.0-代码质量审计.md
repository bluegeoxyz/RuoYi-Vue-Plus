## 2. 前后端契约审计

抽查物业收费与仓储主链路后，前端 API 基址与后端 `@RequestMapping` 整体一致；例如收款均为 `/property/payment`，工作项目均为 `/property/workspace/projects`。本轮未发现可直接定性的 P0/P1 路由错配。

仍需注意：

- 前端使用 TypeScript 的 `number | string` 表达 ID，后端为 `Long`，这是框架常用约定，但超过 JavaScript 安全整数时必须保持字符串传输。
- 新增的上下文 option 接口依赖 Service 二次授权，不能只检查 Controller 是否有 `@SaCheckPermission`。
- 收费与仓储多处代码为单行，静态比较 DTO 字段和事务边界的可读性明显不足。

## 3. 异常与事务

- 收款、冲销、入出库、调拨等多表写入可见 `@Transactional(rollbackFor = Exception.class)`，并使用状态 CAS/行锁，方向正确。
- 应收批次生成捕获单条失败并形成 `PARTIAL_SUCCESS`，属于业务设计；需要运营侧明确失败重跑与幂等流程。
- 全量测试暴露启动失败断言被无关 Bean 创建错误抢先的问题，说明“安全配置缺失时 fail-closed”测试当前不稳定。

## 4. 未使用/疑似废弃代码

本轮未对任何业务类作“确定无用”判定。仅列为候选：

- `ruoyi-demo` 下的示例 Controller、TODO 与硬编码示例路径；是否部署由 profile/module packaging 决定。
- 前端 git 状态中 `RuoYiDoc`、`RuoYiGit` 组件已删除，但这是审计前已有改动，本次不判断是否应恢复。
- workflow 的短信 TODO 和自定义编号 TODO 可能是扩展点，不应直接清理。

可在 TASK-V1-002 优先处理且风险较低的只有：测试脚本补齐、编码配置、测试日志降噪、Lombok 显式注解、纯格式化。deprecated API、migration、事务与权限代码均须先补测试或环境验证。
